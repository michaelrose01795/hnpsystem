# Not following `staffglobal.css` setting

Repository-wide static audit of staff-facing UI that recreates or overrides a shared `staffglobal.css` family. The audit covers badges, buttons, inputs/forms, modal and popup shells, tables, tabs, dropdowns, toggles, toolbars, empty states, and toasts.

- Audit date: 6 August 2026
- Canonical implementation: `src/styles/staffglobal.css`, its imports under `src/styles/families/`, and the shared components in `src/components/ui/` and `src/components/popups/`
- Files scanned: all JavaScript/TypeScript UI files under `src/pages`, `src/components`, and `src/features`, plus CSS modules and feature styles used by staff routes
- Application code changed by this audit: none

## What counts as not following the setting

A finding is included when staff-facing UI locally supplies the core visual properties of a shared family instead of using its canonical class/component, or when it adopts the canonical class but overrides those core properties inline. Layout-only styles such as width, flex placement, grid position, and content-specific alignment are not findings.

Canonical contracts used by this audit:

- Actions: shared `<Button>` or `.app-btn` with an appropriate variant and size. Visual `background`, colour, padding, radius, font, border/ring, shadow, and control height must not be recreated inline.
- Cards, sections, and panels: `LayerSurface`/`LayerTheme` with strict alternation, or an approved wrapper such as `Card`, `Section`, or `SectionCard`. Raw surface background, radius, outline, and card shadow styling is a finding.
- Form controls: `.app-input` plus `--search`, `--select`, or `--textarea` where applicable; purpose-built Calendar, TimePicker, Dropdown, SearchBar, and toggle APIs are accepted shared families.
- Popups/modals: `PopupModal`, `.app-modal`, `.app-popup`, `.modal-panel`, `.popup-panel`, or a documented feature shell such as `VHCModalShell`.
- Tables: `.app-data-table`/`.app-table-shell`; ordinary staff tables are also accepted when `GlobalTableShells` classifies them at runtime and they do not opt out.
- Tabs: `TabGroup`/`.tab-api`, `StaffTabs`, or `.app-tab` variants.
- Status/category/count labels: `.app-badge` with the relevant size/case and exactly one tone modifier.
- Feedback and supporting UI: `.app-toast`, `.app-empty-state`, `.app-toolbar-*`, `.app-toggle-*`, and the shared dropdown family where those semantics apply.

The preferred pattern is:

```jsx
<span className="app-badge app-badge--uppercase app-badge--warning">
  Waiting
</span>
```

Use the base class, add `app-badge--uppercase` only where uppercase presentation is intended, and select exactly one appropriate tone class. Every status badge inherits the shared 44px control height directly from `.app-badge`.

The report also includes partial adoption: elements carrying a canonical class while inline styles still override its core visuals, and manual card/popup shells that borrow one global class but continue to own their surface appearance locally.

## Summary

The expanded audit found **158 confirmed implementation groups**: 54 badge/status groups, 39 button/action groups, 26 form-control groups, 9 popup/modal-shell groups, and 30 card/section/panel surface groups. It also records **1 specialised VHC camera/HUD case** that needs an explicit exception-or-migration decision. A group can contain several instances when one shared component or one page section repeats the same implementation.

The highest-value migrations are the shared families because one change fixes many routes:

1. Job Card header actions, beginning with the custom inline **Check In** button.
2. Shared popup controls: `ConfirmationDialog`, `NextActionPrompt`, `CheckSheetPopup`, and `SavedViewsBar`.
3. Shared badge families: HR `StatusTag`, support `Pill`, invoice `invoiceStatusBadge`, and VHC status components.
4. Large local form/control families in Goods In, Stock Catalogue, New Order, Delivery Planner, Job Card, and HR Employees.
5. Raw nested surface families in Job Card/VHC, Messages, Profile, Next Jobs, and Stock Catalogue.

## Specialised case requiring an explicit decision

The VHC full-screen camera/capture UI contains a recording/device-level status pill and concern-picker status/measurement pills. These use HUD tokens, blur, camera-safe sizing, and pointer behaviour rather than normal page styling. They do not follow `.app-badge`, but blindly replacing them could harm the capture overlay.

- Routes: `/job-cards/[jobNumber]` → VHC capture and `/tech/[jobNumber]` → VHC capture.
- How to see: open a VHC section, start photo/video capture, rotate/tilt the device or start recording, and open the concern picker.
- Sources: `src/components/VHC/mediaCapture/FullScreenCapture.js:333`, `src/components/VHC/mediaCapture/ConcernPanel.js:91`, `ConcernPickerModal.js:155`.
- Recommendation: either create a documented `app-badge` HUD modifier or explicitly allowlist these capture-only primitives. Do not force the ordinary control-height badge into the camera overlay without visual testing.

## Confirmed exclusions

These were reviewed and intentionally not reported as `staffglobal.css` violations:

- **Public/customer website UI:** `src/pages/website`, `src/components/website`, `src/features/website`, `src/singlescroll`, and the 3D public website use `custglobal.css` or isolated public-site CSS, not `staffglobal.css`.
- **Public VHC share/customer pages:** their tabs and counters are outside the staff shell and should be assessed against their own customer-facing styling contract.
- **Shared control APIs:** Calendar, TimePicker, MonthPicker, Dropdown, MultiSelectDropdown, SearchBar, TabGroup/`tab-api`, and documented toggle controls have their own canonical families imported by `staffglobal.css`; their internal buttons/inputs are not expected to wear `.app-btn`/`.app-input` as well.
- **Automatically classified tables:** `GlobalTableShells` adds `.app-table-shell` and the correct heading/rows-only variant to staff tables at runtime. A raw `<table>` is not a violation by itself unless it opts out or overrides the canonical table visuals; no additional confirmed opt-out table violation was found in this pass.
- **Layout-only overrides on canonical controls:** width, min-width, flex, gap, alignment, and content-specific sizing are accepted. For example, the `/appointments` table **Check In** button already uses `app-table-action-btn app-table-action-btn--primary`; its inline min-width is layout-only and is not listed as a button violation.
- **Specialised interactive primitives:** calendar days, dropdown options, scheduler overflow controls, diagram hotspots, media/editor tools, camera shutter controls, timeline handles, and accessibility-only close/hit targets are not ordinary buttons. The VHC capture family is called out separately where a formal exception is still needed.
- **Dot-only indicators:** timeline dots, status LEDs, unread dots, chart legend dots, recording dots, and tyre/brake diagram markers are diagram/notification primitives, not text badges.
- **Progress geometry:** capacity bars, progress rails, scrubbers, sliders, and percentage fills.
- **Avatars and icon circles:** round initials, user photos, plus/minus controls, and circular icon containers.
- **Skeletons:** pill-shaped skeleton blocks intentionally mimic final geometry but contain no status/category content.
- **Canonical examples:** the badge showcase at `/dev/user-diagnostic#badge`, the updated Job Card header status/source/division labels, account tables, invoice tables, activity log, global search, and the Website Manager `StatusBadge`/analytics `Pill` already use the relevant shared family correctly.
- **Non-badge text highlights:** inline highlighted descriptions in `JobProgressTracker` and ordinary labels with a background used as part of a larger diagram or editable control.
- **Toast, empty-state, and toolbar families:** the scan checked bespoke names, roles, and visual patterns but did not produce an additional confirmed bypass that was not already better classified as a surface, popup, button, or status finding above.

## Recommended migration order

1. Fix shared components first: popup action primitives (`ConfirmationDialog`, `NextActionPrompt`, `CheckSheetPopup`), HR `StatusTag`, support `Pill`, `SavedViewsBar`, request autosuggest, invoice status/action components, and VHC shared controls.
2. Convert high-traffic production workflows: Job Card header (**Check In** first), Job Card dialogs, Write-Up, Goods In, Stock Catalogue, Delivery Planner, delivery route, New Order, and technician job Documents/VHC.
3. Move every ordinary native form control in those workflows to `.app-input` or the appropriate shared control API at the same time as its buttons, so a popup is migrated as one coherent unit.
4. Replace manual modal shells with `PopupModal`, `.app-modal`, or the appropriate documented feature shell; then remove redundant overlay/card visual objects.
5. Replace raw card/section/panel surfaces with `LayerSurface`/`LayerTheme` or approved wrappers, checking layer alternation from the outer page shell inward rather than mechanically replacing isolated divs.
6. Convert HR/profile, reports, consumables, clocking/efficiency, loan-car, developer, and vision-only deviations.
7. Decide and document the VHC camera/editor/diagram exception boundary before touching specialised capture controls.
8. Add a static guard that rejects newly added staff-facing raw buttons with visual inline properties, ordinary native controls without `.app-input`, manual `role="dialog"` shells, raw card surfaces, and text-bearing badge/chip/pill implementations without `.app-badge`. Allowlist public scopes and documented specialised APIs.
